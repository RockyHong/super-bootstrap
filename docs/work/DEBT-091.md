# DEBT-091 — the paired pin merges into an already-bootstrapped repo with no veto row

**Logged:** 2026-08-27 · **Source:** consumer sync report (v2.29.7 → v2.39.3) — `mattpocock-skills@mattpocock` landed in `.claude/settings.json` `enabledPlugins` as part of the sync commit with no drift row to decline
**Problem:** [`harness-bootstrap/SKILL.md`](../../plugins/super-bootstrap/skills/harness-bootstrap/SKILL.md) § core pin ("Consequence on an already-bootstrapped repo") states the paired pin's keys merge in silently because pins are missing-or-present, not diff-and-approve, and calls it intended. The consumer effect is a new project-level plugin pin committed to git through a sync whose every other change went through a per-section approval row — the one change with the widest reach (a second plugin's skills become discoverable in every session) is the one the installer could not decline at the moment it landed. [`docs/decisions.md`](../decisions.md) closed "pin mattpocock/skills as a core dep" — this card does not reopen that; it asks whether the *first-time merge on an existing repo* should present a row the installer can set to `false` before the commit, given the drop spelling (`false`, never delete) already exists.
**Area:** `plugins/super-bootstrap/skills/harness-bootstrap/SKILL.md` § core pin (paired-pin consequence paragraph) · § 2c staging list (settings.json row) · `assets/hooks-ensure-infra.md` only if the pin write moves
**Prior:** On sync (not fresh install), a paired-pin key absent from settings.json renders as a `⊕ new` row — accept merges `true`, decline writes `false` — so the drop spelling is offered at the only moment it is cheap; fresh installs keep the unconditional seed.
**Test-feel:** doc-only
**Blast:** local

## Verdict — surface · 2026-08-27

### Findings

- **premise verified — the card names a real classification split inside the skill, not only a posture.** [`harness-bootstrap/SKILL.md`](../../plugins/super-bootstrap/skills/harness-bootstrap/SKILL.md) § Pipeline-owned lists `.claude/settings.json` plugin pins (`enabledPlugins`, `extraKnownMarketplaces`) as **subject to drift check**, and the per-artifact rule just above it turns an absent pipeline-owned section into an `⊕ new` row — "show the template section, get approval, insert". § 2a then carves pins out: "Folders + **core** plugin pin don't drift — only two states: missing or present." That sentence names the core pin only, whose no-veto treatment is earned by its lock (the skeleton's `/super-bootstrap:*` doors and the committed `commit-channel.sh` dangle without it). The § core pin consequence paragraph extends the same carve-out to the paired pin, which the same section declares **not** locked ("droppable per repo", "offered for drop"). The no-row treatment is inherited from a class property the paired pin does not have — that is the mechanism behind the consumer's missing veto row.
- **coverage-gate side effect.** § 2c gates the commit on the sync report carrying a row for *every* pipeline-owned section in scope, and the runway receipt's `covered` list is copied mechanically from those rows. The pins have no row-producing step (the § 2b sample report shows none), so the pin either escapes the gate it is enumerated under or lands a row with no approval semantics. Same split, second symptom.
- **the propose-don't-force branch already exists and is unreachable.** [`resolve-plugins/SKILL.md`](../../plugins/super-bootstrap/skills/resolve-plugins/SKILL.md) Phase 4 § Pre-resolve pins: "**Harness-active + key absent** (repo bootstrapped before the pairing shipped) → propose the pin as the same droppable offer, never as a locked re-pin. A decline writes `false`, not a missing key." That is exactly this card's scenario. It cannot fire in the entry flow: [`super-bootstrap/SKILL.md`](../../plugins/super-bootstrap/skills/super-bootstrap/SKILL.md) dispatches the runway unconditionally *first*, § 2a merges the key as `true`, so resolve-plugins always reads the `true` branch → one drop offer **after** the sync commit already landed the pin. The intent the card asks for is authored in the repo and defeated by step order.
- **a decline channel does exist, post-commit.** The `true` branch re-offers drop on every curation run; an accepted drop writes `false` in resolve-plugins' own commit and is never re-proposed. So the effect is "committed enabled first, declinable second", not irreversible — the card's scope is the *moment*, not the absence of any channel.
- **aim: distinct from the closed fork, but it contests a ratified spec line.** [`docs/decisions.md`](../decisions.md) closes "Bootstrap pins mattpocock/skills as a core dep and harnesses it" → *reopened + answered: pair them*, scoped to "install-plus-prompt (device install left disabled, **per-repo enable at bootstrap**…)". The card sits inside that per-repo-enable arm and does not re-propose pairing — **not a re-walk**. But [`harness-architecture.md`](../specs/harness-architecture.md) § 6 states as decided: "The pin reaches already-bootstrapped repos too, at their next sync, and silently — pins carry no drift diff. Under pairing that is the intended reach, not a leak." Reversing that is an owner posture call, so auto-fix criterion 4 (no user judgment) fails; criterion 3 fails independently (doc-only skill prose, no unit/e2e surface — verification is a cold dry-run of the sync).
- **no duplicate, no precedent.** `docs/work/` grep: DEBT-091 is the only card naming the pin (DEBT-090/092/093/094 come from the same consumer sync but touch hooks, `docs/` pillars, the venue-map skeleton, and a CLAUDE.md line). `git log --grep="paired pin"`: the pairing ship plus the DEBT-059/060 close-out — neither about an approval row.
- **repo profile: matters at the margin, not at the core.** The missing veto at the merge moment is profile-independent — § 2a seeds unconditionally on every already-bootstrapped repo. Profile decides only whether *any* decline follows: the entry skill's one branch is "seed docs substantive?" — substantive → tier-2 curation runs → post-commit drop offer; thin skeleton docs → greenfield branch stops at the resolve gate, no offer that run; and a consumer invoking `/super-bootstrap:harness-bootstrap` directly never reaches resolve-plugins on any profile. A text-first repo with real prose docs most likely reads *substantive*, so the reporter probably did get the post-commit offer — which is why the report lands on the moment, not on the channel. Separately, value is profile-keyed (his lane is code-shaped; § 7's evidence index has his phases driving a runtime red loop) and the skill's own neighbour step § 2a-drain already asks per profile ("Most dev repos: yes. Skill / plugin / docs repos: skip") while the paired pin beside it does not — but making the *seed* conditional on profile changes the "seeded unconditionally" arm and edges toward the closed fork, unlike the row question.

### Decision needed

- **Where does the paired-pin enable earn its decline moment on an already-bootstrapped repo?** § 6's "intended reach, not a leak" answers *whether* it may land silently; it has never been read against § Pipeline-owned's own classification of the pin as drift-checked, or against the unreachable key-absent branch in `resolve-plugins`.
- Options (mutually exclusive on where the decline sits):
  1. **Ratify status quo** — the post-commit drop offer at `resolve-plugins` is the sanctioned channel. Card closes; the § Pipeline-owned bullet gains an explicit "pins raise no row" exception so the classification stops contradicting § 2a, and the reasoning lands where a re-proposal would hit it.
  2. **`⊕ new` approval row at § 2a, sync-only** (the card's Prior) — key absent on a repo that already carries a runway → render the pin as an `⊕ new` row on the existing sync report; accept merges `true`, decline writes `false`. Fresh installs keep the unconditional seed.
  3. **Inform, don't ask** — the pin still merges unconditionally, but § 2b writes a sync-report row for it and the done-summary names the landed pin plus the `false` drop spelling. Closes the "silently" half, leaves the veto at curation.
  4. **Move the paired-pin write out of § 2a into `resolve-plugins`** — revives the key-absent branch as the single enable door. The pin then reaches only repos where tier-2 curation runs, changing the "seeded unconditionally like a core dep" arm.
- **recommendation: 2.** Smallest change that leaves the pairing decision intact — the pin still reaches every synced repo unless actively declined — while resolving the § Pipeline-owned / § 2a split that produced the gap, riding the sync-report mechanism that already exists, and preserving the load-bearing spelling (a decline writes `false`, never a missing key). Two consequences belong in the row's prompt text: the decline is **durable** (`resolve-plugins` never re-proposes a `false` pin), and § 6's silent-reach line plus the coexistence-runbook and techstack mirrors must be rewritten in the same change or the specs contradict the shipped skill. Option 4 is the cleaner single-door design but pays with repos that never run curation; option 3 is cheapest and still leaves the widest-reach change undeclinable at the moment it commits.
