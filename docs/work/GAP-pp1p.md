# GAP-pp1p — The `SESSION-STATE/` carry ledger has no lifecycle, so stale carries accumulate

**Logged:** 2026-11-26 · **Source:** mailbox note from `jowagoko` (handoff, 2026-11-25), observed against plugin 7.1.2
**Problem:** Stale carries build up in the root `SESSION-STATE/` ledger. In jowagoko on 2026-11-25 the ledger held 11 carries and 7 were stale: 4 named a card already resolved and deleted (one BUG, three on the same GAP card); 2 held a Next step that the card's own latest `## Progress` already recorded as done; 1 was a 17-day-old pointer-only stub duplicating two newer carries on the same card. One card collected three carries from three sessions; the 4 live carries spanned 0–8 days. Mechanisms the sender saw: only the owning session clears its carry (done-close touches its own file only), so a session that never closes, or a later session that finishes the work without picking that carry, leaves it behind; `session-continue` filters gone-pointer carries out of its offer but writes nothing, so the same dead files are re-read every pickup; nothing compares a carry's Next step against the card's newer Progress; several sessions parking on one card each write a carry and nothing merges or retires the older ones. Open design: who may retire a carry whose pointers are gone or whose card moved past it; whether a newer carry on the same card supersedes older ones; whether `session-continue` / `session-close` / `needs-me` offer that retirement in their existing pick. (scope per the jowagoko note, unconfirmed)
**Area:** `plugins/super-bootstrap/skills/session-close/SKILL.md`, `plugins/super-bootstrap/skills/session-continue/SKILL.md`, `plugins/super-bootstrap/skills/needs-me/SKILL.md`
**Prior:** The ledger convention defines write and clear by the owning session only; no retirement path exists for a carry its owner never closes.
