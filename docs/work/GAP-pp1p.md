# GAP-pp1p — The `SESSION-STATE/` carry ledger has no lifecycle, so stale carries accumulate

**Logged:** 2026-11-26 · **Source:** mailbox note from `jowagoko` (handoff, 2026-11-25), observed against plugin 7.1.2
**Problem:** Stale carries build up in the root `SESSION-STATE/` ledger. In jowagoko on 2026-11-25 the ledger held 11 carries and 7 were stale: 4 named a card already resolved and deleted (one BUG, three on the same GAP card); 2 held a Next step that the card's own latest `## Progress` already recorded as done; 1 was a 17-day-old pointer-only stub duplicating two newer carries on the same card. One card collected three carries from three sessions; the 4 live carries spanned 0–8 days. Mechanisms the sender saw: only the owning session clears its carry (done-close touches its own file only), so a session that never closes, or a later session that finishes the work without picking that carry, leaves it behind; `session-continue` filters gone-pointer carries out of its offer but writes nothing, so the same dead files are re-read every pickup; nothing compares a carry's Next step against the card's newer Progress; several sessions parking on one card each write a carry and nothing merges or retires the older ones. Open design: who may retire a carry whose pointers are gone or whose card moved past it; whether a newer carry on the same card supersedes older ones; whether `session-continue` / `session-close` / `needs-me` offer that retirement in their existing pick. (scope per the jowagoko note, unconfirmed)
**Area:** `plugins/super-bootstrap/skills/session-close/SKILL.md`, `plugins/super-bootstrap/skills/session-continue/SKILL.md`, `plugins/super-bootstrap/skills/needs-me/SKILL.md`
**Prior:** The ledger convention defines write and clear by the owning session only; no retirement path exists for a carry its owner never closes.

### Decision needed

- Who may retire a carry that is not its own, and on what signal? The own-file rule exists so that one session cannot destroy a concurrent live session's carry (`session-continue/SKILL.md:44`: "a live session's carry is only claimable when the user — who alone knows what else is running — hands it over"). Any retirement path crosses that boundary. The fork is where the user's gate sits and which signals qualify.
- options:
  - **A — session-continue offers retirement in its existing pick.** It already reads every carry and computes staleness. It adds a **retire** option (multi-select or grouped) for: (1) carries with a gone load-bearing pointer; (2) carries whose card's latest Progress post-dates the carry, shown with the carry's Next step beside that Progress line so the user judges "already done"; (3) older carries on a card that a newer carry also anchors. A carry is deleted only on the user's pick. The deletion is a second write beside the claim rename, and session-continue's "one write" rule widens to cover it. session-close keeps own-file-only.
  - **B — session-close sweeps sibling carries.** It mirrors its finished-card sweep (`:62`): a **retire** move per dead sibling carry in the one confirm-pick. This breaks its "no read-pass over the folder" rule, and it adds a folder read to every close, including closes where no carry is dead.
  - **C — automatic retirement by rule, without a pick.** Gone-pointer carries are deleted mechanically (a deleted card = resolved), and a newer carry on the same card supersedes older ones. This is the cheapest option. It is the only one that deletes another session's file without the user's gate, and "newer supersedes" can drop a live parallel thread on the same card.
- recommendation: A. session-continue is the one skill that already reads every carry and computes the stale verdict (`:34`). The resume pick is already the user gate for touching another session's carry (`:44`). A therefore reuses both the evidence and the gate, and adds no new read pass and no ungated delete. needs-me's count line should count live carries, or say "N carries (M stale)", so the pointer does not overstate. That is a small rider on A, not a separate fork.
- settles by: preference / risk authority (the user owns the accountability for deleting another session's carry, and the own-file boundary is a ratified safety rule in the ledger SSOT). After the ruling, the build is behavior-shaping skill prose. Per `.claude/rules/skill-authoring.md` it takes a RED micro-test first (`phased build`: a fixture `SESSION-STATE/` holding the jowagoko shapes — a gone-card carry, a done-next-step carry, a duplicate stub, a live carry — walked by a cold session-continue on old vs new text), then `audit-harness-edits`. Test strategy for the eventual fix: e2e (fixture walk). It needs no human eyeball.

## Design — 2026-11-26

Option A, settled on the user's delegation ("直接開始做", 2026-11-26 — pick by the verdict's recommendation). session-continue's existing pick gains a **retire** option for carries it already judges: (1) a gone load-bearing pointer; (2) the card's latest Progress post-dates the carry — shown with the carry's Next step beside that Progress line; (3) an older carry on a card a newer carry also anchors. Deletion only on the user's pick; session-continue's one-write rule widens to claim-rename + picked retirements. session-close stays own-file-only. Rider: needs-me's count line reports `N carries (M stale)`. Shipped doctrine `assets/harness.md` § Context Hygiene ledger-owner line updates, placed copy refreshed byte-identical.
