# BUG-068 — Fresh-install sync report never shown to the user

**Logged:** 2026-09-23 · **Source:** sender-session research — RockyGamesKnowHow greenfield bootstrap on v2.52.1 (transcript `e9abf748`), GAP-087 grounding; GAP-087 measurement run — cold Opus greenfield bootstrap of an empty temp repo from the dev copy
**Problem:** harness-bootstrap §2c says the sync report is always shown before commit; on a fresh install the sender session announced one line and deleted the report after commit — Block 1 and the Phase 3 handoff prose were never rendered. Unclear whether an all-`⊕ new` fresh install is meant to render the full table; the `⊕ new` verdict (defined as section-absent, Block 2 approval) also sits oddly against the promptless missing-file write.
**Area:** `plugins/super-bootstrap/skills/harness-bootstrap/SKILL.md` §2b-§2c, Phase 3

## Verdict — surface · 2026-09-23

### Decision needed

- What does a fresh install render at §2c, and how is the render forced so it stops collapsing? Options are mutually exclusive on the render shape; each carries the same settled sub-fix.
- (A) Keep `:586` as written — full all-`⊕ new` table + Phase 3 block on fresh — and add a forcing function per § Principles:5 (render step gated the same way the file is: e.g. Phase 3's block becomes the runway's return value that `setup` § Disclosure prints verbatim above its heads-up line; `:653` cleanup ordered *after* the render step). Executor breach acknowledged; spec hardened.
- (B) Spec change — fresh install renders a one-line coverage summary (`{N} sections placed, all ⊕ new — inventory: git show --stat HEAD`) in place of the row table; Phase 3 First-run block stays mandatory and gets the same forcing function as (A); full table stays a re-run surface (`:586` rewritten, `:139` "all new" kept as the row verdict).
- (C) No spec change — close as executor error, rely on `:416` / `:586` prose as is.
- Settled sub-fix riding (A) or (B), not user judgment — reconciled from the spec's own text: a section in a file this run wrote takes row verdict `⊕ new` (`:139` / `:586`), resolution `seeded` (`:594`), no Block 2 (`:142` / `:352` promptless write; `:441`'s expansion is scoped to an *existing* file — state that scope at `:426`); add `seeded` to the `:584` gate's resolution set. ## Design — 2026-09-23

Option (B) from the Verdict, settled by the gateway under the user's delegation (hygiene and earn-right first; downstream reach across many repos): a fresh install renders a one-line coverage summary in place of the all-`⊕ new` row table — the table's protective purpose (review what is about to be overwritten) has nothing to protect on fresh, so it fails the cut test — while the Phase 3 First-run block stays mandatory; the full table remains a re-run surface. Forcing function takes the shape the repo already uses for a must-render surface: a fenced literal block marked render-verbatim (the resolve-gate block in `setup/SKILL.md` is the precedent), ordered before the `:653` report cleanup, so the render leaves the same residue the file does. The settled sub-fix rides along: a section in a file this run wrote takes row verdict `⊕ new`, resolution `seeded`, no Block 2 (scope `:441`'s expansion to an existing file at `:426`); `seeded` joins the `:584` gate's resolution set. RED per `skill-authoring.md`: micro-test the new §2c wording against the current text on the fresh-install scenario — a full greenfield render is not required for the floor.
