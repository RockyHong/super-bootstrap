# BUG-072 — commit-channel.sh reads a quoted `|` as a command separator

**Logged:** 2026-09-23 · **Source:** GAP-087 follow-up research subagent (main-session commit-door bypass sweep)
**Problem:** A read-only subagent command `git -C <repo> log … | grep -i -E "…|wrong commit|…"` was denied as a raw commit: the hook's separator regex treats the `|` inside the quoted grep alternation as a command boundary, so `wrong commit` in the pattern reads as a `git commit` invocation. False positive on read-only commands that merely mention "commit" after a quoted `|`.

### Root cause (verified)

`commit-channel.sh:35`:

```
_re='(^|[;&|'"$_nl"'])[[:blank:]]*git[[:blank:]]+([^[:space:]]+[[:blank:]]+)*commit([[:space:]]|$|;|&|\|)'
```

The card's stated mechanism — the leading separator alternation reading the quoted `|` as a command boundary — is **not** what fires. Direct evidence: the same alternation on a non-git-anchored line, `grep -i -E "bypass|wrong commit|x" file`, is **allowed**; after the quoted `|` the next token is `wrong`, not `git`, so `(^|[;&|\n])[[:blank:]]*git` never anchors there. What matches is the `^git` anchor at the line start plus the global-flag walker `([^[:space:]]+[[:blank:]]+)*`: its token class `[^[:space:]]+` accepts `|`, `;`, `&&`, `grep`, `-i`, `-E`, `"bypass|wrong` as "global flags", so the span from the leading `git` reaches across the pipe to the word `commit` inside the grep pattern, and the trailing boundary `([[:space:]]|$|;|&|\|)` accepts the quoted `|` after it. Two controls pin both halves: `git log --oneline | grep -i "wrong commit"` is **allowed** (closing `"` is not a boundary), `git log -S commit --oneline` is **denied** (space after `commit`, no pipe needed).

Consequence: the class is wider than "quoted `|`" — any git-anchored chained or piped line that later mentions `commit` followed by whitespace / `|` / `;` / `&` / end denies. 90-day local transcript sweep (deny events paired to their `tool_use` command; both the `hook error:` and the older `Error:` wrappers counted): **6 organic false denies across 3 repos in 14 days** (Magnetized Remake 09-10 `git log --oneline -4 && echo "--- files in HEAD commit ---" && git show …`, 09-12 `git status … && echo "--- P1 commit ---" && git show …`; super-bootstrap 09-12 `… && echo "=== first commit date ===" && git log …`, 09-21 `git log … && echo "=== full commit msgs ===" && git log …`, 09-23 the card's incident; claude-config-manager 09-20 `git show … ; echo "=== commit msg ==="; git log -1 …`) against **0 genuine catches** of a subagent committing a real repo in the window (the two real `git commit` denies were scratch-fixture repos under a research probe). Aim check — earn-right: the class recurs organically at roughly one per 2–3 days across the runway fleet, and the whole of the hook's observed deny output in the window is false positives; the frozen-asset touch buys a behavior change, not the zero-behavior cost `docs/decisions.md:56` rejects. That row closed *widening* enforcement (its reopen bar: a subagent lands a commit through a bypass); this card *narrows* a false positive and leaves the bar untouched — no re-walk. No overlapping open card in `docs/work/`.

Fix (one token): stop the walker at the three separator characters the leading alternation already treats as boundaries —

```
([^[:space:];&|]+[[:blank:]]+)*
```

Verified against every current suite case shape plus the six telemetry commands (tightened regex tested side-by-side with v6): all six false positives → pass; every real-invocation shape stays matched — `git commit -m x`, `git -C /x commit -m x`, `git --no-pager commit -m x`, `git -c core.pager=cat commit -m x`, `git add -A && git commit -m x`, `git add -A; git commit -m x`, newline-separated, PowerShell-shaped, heredoc body line (B1 trade, still denied). DEBT-010's quoted substring still passes.

Residual, out of scope (name in the header comment, do not chase): (a) a literal separator directly before `git … commit` inside quotes — `grep -rn "foo|git commit|bar" docs` — still denies; (b) `commit` as a bare argument of a non-commit subcommand on a git-anchored unchained line — `git log -S commit --oneline` — still denies. Both are the same visible-false-deny-over-silent-pass trade the header already ratifies for the heredoc line; fixing them means quote/subcommand parsing, the unbounded-heuristic class `docs/decisions.md:56` and `:78` close. (c) One new silent pass: a separator character inside a quoted global-flag value before `commit` — `git -C "a|b" commit -m x` — passes under the tightened walker; exotic, accept.
