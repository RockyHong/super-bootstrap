### Decision needed

**1 — Which pin class does the pairing take?** `resolve-plugins` Phase 4 has exactly two: **locked core pin** (never proposed for drop, trust signals never re-fetched, and `:175` requires naming "what breaks" on removal) and **adaptive pick** (re-scored and re-proposed every run). The aim fits neither — the enable is unconditional like a core pin, but nothing breaks when he is dropped, and a repo must be able to drop him.

- (a) Add a third class — *paired pin*: seeded unconditionally at 2a, surfaced in Phase 4 as droppable, never re-proposed once dropped (the `false` value persists the drop through §2a's existing skip rule).
- (b) Treat as a locked core pin — smallest diff, but Phase 4's never-propose-drop clause contradicts the aim's droppability.
- (c) Seed at 2a but classify as an ordinary adaptive pick — no new class, but `resolve-plugins` then re-fetches trust signals and can re-propose him every run, and `:170`'s "a process harness is an ordinary adaptive pick" stays literally true while the 2a pin says otherwise.
- recommendation: **(a)** — the only option that states the aim as written, and its persistence mechanism already exists (§2a `key present → skip`); (b) and (c) each override one half of the aim.

**2 — Where does "awareness of his commands" live, given that a disable must need no doc change?** The shipped skeleton names no foreign command today, and §2a's own dangling-rule warning ("if CLAUDE.md names a skill that isn't installed, the trigger rule misfires silently") is the reason.

- (a) Ship nothing in the skeleton — awareness is his own `## Agent skills` block, written by his setup at step 4. A disable leaves only his artifact behind; sb-owned prose stays bare and the §4 grep contract takes one narrower dent (pin + recipe asset only).
- (b) Conditional CLAUDE.md skeleton block naming his lane picks, written only when the enable happened — richest awareness, but a disable then *does* require a doc change, and it re-buys the dangling-name class.
- (c) Seed a cold `docs/`-side runbook (the coexistence runbook's § Lane picks, shipped) — zero ambient cost, no dangling trigger; a disable leaves a stale doc rather than a stale ambient line.
- recommendation: **(a), plus the command names in the Phase 3 handoff message** (`SKILL.md:550`) — handoff text is transient chat output, not a committed doc, so it carries awareness at the one moment it is actionable and needs no unwind on disable. That keeps "no doc change to drop him" literally true of every sb-owned surface.

**3 — Does the §4 grep contract get scoped or spent?** The card says "deliberately spent". [`harness-architecture.md`](../specs/harness-architecture.md) §6 makes a hit outside the sanctioned class a **regression tripwire**, so spending it outright removes the guard protecting change A's de-coupling.

- (a) Add a second sanctioned hit class — *setup-time composition* (the 2a pin entry, the tracker-recipe asset, the Phase 3 handoff string), with the runtime claim ("super-bootstrap names zero foreign skills at runtime") restated and still grep-verifiable.
- (b) Retire the contract; rely on §6 prose alone.
- recommendation: **(a)** — the contract's value is catching an *unintended* re-coupling, which pairing does not stop needing; a named, enumerable exception class preserves the tripwire at the cost of one pattern change.

**Out-of-scope note (device config — `/contribute` lane, not this repo's to fix):** `~/.claude/settings.json` currently carries `"mattpocock-skills@mattpocock": true`, so the runbook's "installs once at device scope and sits **disabled** there" is not yet true of the authoring device. The build should not assume the device posture already holds.

## Design — 2026-08-10

All three Verdict decisions answered by the owner; the aim itself is unchanged.

**1 — pin class: a third class, `paired pin`.** Seeded unconditionally at `harness-bootstrap` §2a; surfaced in `resolve-plugins` Phase 4 as **droppable**; never re-proposed once dropped; trust signals not re-fetched. The locked-core clause requiring "what breaks on removal" does not apply — nothing breaks, which is exactly why neither existing class fits. The drop spelling is load-bearing: a repo drops him by setting `"mattpocock-skills@mattpocock": false`, **not** by deleting the key — §2a merges absent keys on every sync, so a deleted key returns. That spelling ships stated, not implied.

Pin shape: `enabledPlugins` entry `"mattpocock-skills@mattpocock": true`, plus `extraKnownMarketplaces.mattpocock` → source `github`, repo `mattpocock/skills`.

**2 — awareness lives in the handoff, not the skeleton.** The shipped `CLAUDE.md` skeleton names no mattpocock command. Awareness is carried by his own `## Agent skills` block, written by his setup at its step 4, plus the command names in `harness-bootstrap`'s Phase 3 first-run handoff message — transient chat output, not a committed doc, delivered at the one moment it is actionable. This keeps "dropping him requires no doc change" literally true of every super-bootstrap-owned surface, and avoids re-buying the dangling-name class §2a already warns about.

**3 — the §4 grep contract is scoped, not spent.** [`harness-architecture.md`](../specs/harness-architecture.md) §4 gains a second sanctioned hit class — **setup-time composition** — enumerating exactly three permitted hits: the §2a pin entry (+ its marketplace), the tracker-recipe asset, and the Phase 3 handoff string. The runtime claim is restated and stays grep-verifiable: super-bootstrap names zero foreign skills **at runtime**. Deliberate coupling becomes expressible; accidental re-coupling stays caught.

**Forced by ground truth, not chosen:**

- Part (3) of the aim is **prompt + recipe, never perform** — the installed `setup-matt-pocock-skills` carries `disable-model-invocation: true` and `harness-bootstrap` runs as a model.
- Bootstrap must **not** pre-write `docs/agents/*` — his write step has an in-place rule for the `## Agent skills` block only, so a seeded destination file may simply be overwritten. The recipe ships as a paste-able asset.
- The third pin lands in **already-bootstrapped** repos at their next sync, silently (pins carry no drift diff). Under pairing that is intended; it ships as a stated consequence.

**Out of scope, routed:** device-scope posture (`~/.claude/settings.json` currently has him `true`) → `/contribute` lane. Whether `andrej-karpathy-skills` retires under his coverage → [`GAP-057`](GAP-057.md).
