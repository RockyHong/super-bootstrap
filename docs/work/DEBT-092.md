# DEBT-092 — § 2a-scale plants three `docs/` pillars without telling the installer to update a repo-local doc-routing rule

**Logged:** 2026-08-27 · **Source:** consumer sync report (v2.29.7 → v2.39.3) — the consumer's own `.claude/rules/doc-ownership.md` requires a routing-table row per new `docs/` pillar; the sync left the table short by three and the post-sync cold audit flagged it as a major finding, fixed forward in a second commit
**Problem:** [`harness-bootstrap/SKILL.md`](../../plugins/super-bootstrap/skills/harness-bootstrap/SKILL.md) § 2a-scale places `docs/parked.md`, `docs/test-queue.md`, `docs/outward.md` and closes with "Stage the placed files with the Phase 2c commit." Nothing in the step tells the installer that a repo may carry its own gate on new `docs/` pillars (a routing table, an ownership rule, a docs index) and that those need a row for each placed file. The skill cannot know the rule's shape, but it does know it just created three durable pillars — the moment to prompt the sweep is there and unused.
**Area:** `plugins/super-bootstrap/skills/harness-bootstrap/SKILL.md` § 2a-scale (closing line) · possibly § 2b-adopt (same gap when adopt mode plants a container)
**Prior:** One closing sentence in § 2a-scale: the placed files are new `docs/` pillars — a repo-local rule or index that enumerates `docs/` pillars (routing table, ownership rule, docs index) gains a row per placed file in the same commit.
**Test-feel:** doc-only
**Blast:** local

## Verdict — surface · 2026-08-27

### Findings

- **Premise verified, by direct read.** [`harness-bootstrap/SKILL.md`](../../plugins/super-bootstrap/skills/harness-bootstrap/SKILL.md) § 2a-scale's `y` branch places the five `assets/scale/` skeletons and closes with "Stage the placed files with the Phase 2c commit." A grep of the whole skill plus `shared/` for a consumer-side enumeration prompt (`repo-local` / `consumer-local` / `index that enumerates` / `routing table`) returns exactly one hit — SKILL.md:319, the CLAUDE.md § Rules `venue-map.md` bullet rule — and nothing about repo-authored surfaces. The claim holds as written.

- **Plugin gap, not consumer-fit** — three grounds, in directness order:

  **(i) The plugin already performs this registration for the one enumerating surface it owns.** [`assets/claude-md-skeleton.md`](../../plugins/super-bootstrap/skills/harness-bootstrap/assets/claude-md-skeleton.md) § Planning carries the three pillars as conditional lines (165–167), and § 2b's per-doc handling gives CLAUDE.md § Rules an explicit `⊕ new` / drift rule for the shipped `venue-map.md` bullet (SKILL.md:319). "A new `docs/` pillar earns a row in whatever surface enumerates pillars" is therefore already the skill's own model — it stops at the surfaces the plugin authored. The consumer-authored instance is the same class, unhandled.

  **(ii) No downstream door can catch it.** § 2c commits through [`/super-bootstrap:commit`](../../plugins/super-bootstrap/skills/commit/SKILL.md), which carries no scaffold exemption (its skips are deferred mode and the `docs/work/` card-lifecycle lane). But [`doc-sync-scan`](../../plugins/super-bootstrap/agents/doc-sync-scan.md) step 1 reads the consumer's **CLAUDE.md § Doc Sync** as the surface owner, and that section scopes the surface to `docs/**` plus the root README and plugin READMEs, and declares `.claude/rules/` read-only harness — flag, never write. A consumer's `.claude/rules/doc-ownership.md` is thus both outside the enumeration and outside the write boundary. Compounding it: a freshly planted pillar has zero reverse-citers and zero link-targets, so the mechanical enumeration (term-grep · reverse-citer · link-target) has nothing to pull toward the stale table. The planting step is structurally the only moment.

  **(iii) Not specific to the reporting consumer's profile.** Surfaces that enumerate `docs/` pillars are ordinary harness furniture, not doc-governance exotica: a rule's `paths:` frontmatter glob (this repo's own [`venue-map.md`](../../.claude/rules/venue-map.md) lists two `docs/` paths), a README docs map, a docs index, a CI docs-lint path list. A text-first repo hits it more often, not uniquely. Recurrence is the sharper signal: four durable-artifact plantings reached already-bootstrapped repos in ~10 weeks through three different steps — `docs/decisions.md` (`d6a941e`, § 2a always-created), the scale trio (`e9fecd9`), root `CODING_STANDARDS.md` (`f17361d`, § 2a always-created), `docs/outward.md` (`c3f4171`, § 2a-scale). The reported miss is the fourth instance of a repeating event, not a one-off.

The carded "same gap when adopt mode plants a container" is falsified as stated. What adopt mode does carry is the **mirror-direction** case — an approved deletion can leave a consumer's own enumeration naming an artifact that no longer exists — same blind spot, opposite sign, equally out of the commit door's reach.
  - § 2a's always-created macro and § 2b's asset table **are** pillar planters and share the gap verbatim; the class has already landed through § 2a twice (`d6a941e`, `f17361d`). A fix scoped to § 2a-scale's closing line closes the reported instance and misses the next one.
  - The **backfill lane needs no separate anchor**: an existing scale-module consumer receiving `outward.md` gets it either through the re-offered § 2a-scale `y` branch (its arming signals still hold once installed) or through the per-artifact "Missing → write" applied to the § Pipeline-owned scale rows — both inside § 2a-scale's text.

- **Scope reach.** Producer-side only; every path is this repo's own product, no served or imported copy in the surface.
  - [`skills/harness-bootstrap/SKILL.md`](../../plugins/super-bootstrap/skills/harness-bootstrap/SKILL.md) — § 2a (always-created macro), § 2a-scale (closing line), § 2b (per-doc handling), § 2b-adopt (deletion mirror), the drift-check row contract at SKILL.md:373, the § 2c gate + staging list at SKILL.md:520.

### Decision needed

- **Where does planted-artifact registration fire, and does it ride prose or the 2c forcing function?** The gap is one step's blind spot only if the scale module is the last durable artifact this plugin ever adds; the commit history says otherwise. And the skill's own closing § Principles — "Mandatory checks ride a forcing function, not prose — a step the model is merely told to 'always run' collapses into a confident assertion on re-runs where the surface looks done" — bears directly on the carded fix shape, since a sync re-run is exactly the surface-looks-done case.

- **Options**
  1. **Carded scope — one closing sentence in § 2a-scale.** Smallest diff, closes the reported instance, fires at the right moment. Leaves § 2a's always-created macro and § 2b uncovered, so the next pillar (two precedents in 10 weeks) re-logs this card; prose-only against the § Principles line.
  2. **Prose at every planting step** — the same sentence at § 2a, § 2a-scale, § 2b, plus the deletion mirror at § 2b-adopt. Covers the class; three-to-four copies of one rule to keep in step, still prose-only, still decays on re-runs.
  3. **One Phase-2 rule + a sync-report row gated at 2c** *(recommended)*. State it once beside the per-artifact rule — a durable artifact newly placed or deleted this run earns a row in whatever repo-local surface enumerates `docs/` pillars or harness artifacts (routing table, ownership rule, docs index, a rule's `paths:` glob); the plugin cannot know its shape, so it asks — and give it a report row per planted/deleted artifact carrying a Block-2 resolution (`row added` / `n-a`). The § 2c gate already halts on an unresolved `⊕ new` row (SKILL.md:520) and the receipt already derives from those rows, so the forcing function is reused, not built. Widest reach; touches the § 2c gate wording and the row contract at SKILL.md:373.
  4. **Consumer-fit — no plugin change.** The consumer's post-sync cold audit did catch it and fixed forward in one commit. Falsified by ground (ii): no shipped door reaches a `.claude/rules/` gate, so this option assumes every consumer runs a cold audit after every sync.

- **recommendation: 3.** Grounds (i) and (iii) put the need on the plugin side, and recurrence across three planting steps makes a step-scoped fix a card that re-logs on the next pillar. Option 3 is also the only one the skill's own § Principles endorses — it hangs the check on the produce-then-judge artifact that already exists instead of adding a fourth "always remember" line. If blast is the worry it splits cleanly: the Phase-2 rule sentence lands first (covers all planting steps, doc-only), the report row + gate clause second.

- **note for the implement phase.** Whichever option lands, the § 2b-adopt arm is a **deletion** case, not a planting one — the card's Area line must not be implemented as written. Harness-file edits take `load-harness-principles` pre and `audit-harness-edits` post; behavior-shaping skill prose takes a RED cold probe first per [`.claude/rules/skill-authoring.md`](../../.claude/rules/skill-authoring.md).
