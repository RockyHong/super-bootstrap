# GAP-100 — the sb↔ccm ownership boundary is undeclared at the routing doors, so findings round-trip

**Logged:** 2026-10-07 · **Source:** `DEBT-126` scenario split (user, in-session); repo record `docs/decisions.md` rows 39 / 40 / 61
**Problem:** super-bootstrap and claude-config-manager each route a finding to the other by **provenance** — whose tree currently serves the file — but the question in dispute is **concern-ownership**, whose problem it is. Provenance is mechanically checkable from one side alone; concern-ownership needs both repos' scope definitions, and each session holds one. When the two diverge, both sides' routing rules fire toward the other with no tie-breaker, and the item moves back and forth. Every hop re-grounds cold without the sender's decision history, applying a criterion that cannot decide the question being asked.
**Area:** `.claude/rules/repo-boundary.md` § Finding lanes; `docs/specs/harness-architecture.md`; claude-config-manager `.claude/rules/skills.md` (consumer-feedback routing) — storehouse-side, `/contribute` only
**Blast:** cross-repo
**Prior:** The criterion that actually decides already exists in this repo, scoped to the wrong job — see the Design block.

## Design — 2026-10-07

Settled whole here, both halves, **before any hand-off**. The user's constraint: a half-settled `/contribute` would be triaged cold by the receiver, which would form its own ownership view — reproducing this card's own bug. Device `CLAUDE.md` § Repo boundary already binds it ("send only a settled judgement whose remaining work is the receiver's by ownership — an unsettled one loops back as buck-passing"), so the storehouse half ships as **transcription-grade** exact text, carrying no judgment for the receiver to make.

### The criterion is not new — it is this repo's own, mis-scoped

`.claude/rules/repo-boundary.md` § Taste-coupling layers already states it: "Judge a skeleton line by whether it resolves in a repo that has **only the installed plugin, nothing of the author's**." That is a concern-ownership test. It is currently applied only to **skeleton prose**, while the routing doors (this repo's provenance classes; the storehouse's `inbox/` lane) check **provenance**.

`docs/decisions.md` row 61 confirms the criterion already decides ownership in practice, twice, while provenance never moved: the doc-consult hook was CCM-planted throughout. Original rejection — "the consult catalog enumerates two layers — project `docs/` plus the author's personal guidelines lore, **which consumer repos lack**". Reopen condition — "Reopen only if sb's product scope expands to own consumer-facing prompt-time doc recall **with a consumer-resolvable catalog**". What fired it — "the catalog became **consumer-resolvable** when the guidelines layer was split out of the deriver". Both calls were correct; what changed was the artifact, not the criterion. So the defect is placement, not absence.

### Criterion, as it lands

Does the artifact have to resolve in a repo holding **only the installed plugin, nothing of the author's**?

- **Yes** → super-bootstrap's concern. The storehouse retires any duplicate copy it holds.
- **No** (it only resolves where the author's device layer exists) → the storehouse's concern. This repo's shipped skeletons must not reference it — already binding under § Taste-coupling layers.

Total: every item falls on one side. Two edges, both already decided by row 61, so neither is a fresh judgment:

- Test surface or bench living on the other side is **not** a reason to leave ownership there — row 61 shipped "the bench moved to `bench/consult-hook/` so the test surface travels with the SSOT". **Test surface travels with ownership.**
- Consumer-resolvable **and** also running in the author layer → super-bootstrap owns, storehouse retires its copy (row 61's shipped outcome).

### Half 1 — this repo

1. `.claude/rules/repo-boundary.md` § Finding lanes gains an ownership step **before** the provenance classes. Provenance keeps its job — naming whose tree holds the file and therefore which door a *write* goes through — but stops standing in for ownership. A finding on a served file whose concern is this repo's is logged here, not contributed out.
2. `docs/specs/harness-architecture.md` declares the seam its own title promises and currently omits: super-bootstrap (per-repo consumer product) against claude-config-manager (device author storehouse), criterion as above. Verified absent at logging: `claude-config-manager` / `storehouse` / `ownership` return zero hits in that file, which declares only the seam against a foreign process harness.

### Half 2 — storehouse, via `/contribute`, transcription-grade

claude-config-manager `.claude/rules/skills.md` consumer-feedback routing gains the same lookup, as an absorption gate on `/digest-inbox`: an inbound item is absorbed only after the consumer-resolvability test; passing it means the concern is the consumer product's, so the item returns **with that verdict** rather than landing lore, and the storehouse retires any duplicate it holds. Provenance does not decide it, and a bench held there is not a reason to keep a consumer-facing concern.

The exact text for that edit is authored in this block's implementation and carried verbatim in the `/contribute` note — the receiver transcribes, it does not judge. Executor of the `/contribute` step is the author, not the session.
