# BUG-8zwv — Commit door's shared-index staging does not isolate concurrent sessions in one checkout

**Logged:** 2026-10-20 · **Source:** device note from `magnetized-remake` (D:/Git/Games/Magnetized Remake, runway 5.2.0), 2026-10-16
**Problem:** Several sessions in one checkout share one `.git/index`; a plain `git commit` commits the whole index tree, and the §5 readback cannot protect against it. Observed in the consumer: (a) session A commits through a private `GIT_INDEX_FILE`, the shared index still holds A's paths at their old blobs, and session B's `git add <own paths>` + `git commit` reverts A's changes and deletes A's new files (commit `68bb558c`) — the readback flags only extra foreign staged paths, not "index entry older than HEAD while the worktree matches HEAD"; (b) A stages into the shared index, the readback finds another session's paths and stops to ask, and meanwhile the other session's plain commit takes A's 41 paths (`763ebb8a`).
**Area:** `plugins/super-bootstrap/skills/commit/SKILL.md` §5
**Prior:** Never stage into the shared index: `GIT_INDEX_FILE="$(git rev-parse --git-dir)/index-<session-id>" sh -c 'git read-tree HEAD && git add -- <paths> && git commit -F <msg>'` in one command, then `git reset -q HEAD -- <committed paths>` on the shared index and delete the private index; readback reads the private index. Consumer rule: Magnetized Remake `docs/dev-harness.md` § Commit from a shared checkout. Related: GAP-1a4e.
