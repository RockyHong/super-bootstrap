# BUG-034 — release tags lose their `## ` section headings; the shipped template carries the defect downstream

**Logged:** 2026-08-09 · **Source:** observed while tagging v2.30.2 — the notes went in with `## Fixes` / `## Other`, the tag came out with neither
**Problem:** `git tag -a` defaults to `--cleanup=strip`, which deletes every line beginning with `#`. The release protocol's step 4 prescribes release notes shaped as `## What's New` / `## Fixes` / `## Other`, and step 5 passes them straight to `git tag -a … -m`, so every heading is silently removed and the tag reads as an unlabelled bullet list. Confirmed on `v2.30.1`, whose annotation starts at the first bullet with no `## Fixes` above it. `v2.30.2` was re-annotated by hand with `--cleanup=verbatim` before push, so it is the only correct one. The defect is not local to this repo: `plugins/super-bootstrap/skills/release-init/assets/template.md` is the shipped asset every consumer's generated `/release` skill is written from, so each of those repos strips its own tag headings the same way.
**Area:** `plugins/super-bootstrap/skills/release-init/assets/template.md:118` (`git tag -a v{version} -m "<release notes>"`) and `:150` (per-platform tag line, same shape); `.claude/skills/release/SKILL.md:112` (this repo's own generated copy, same line)
**Prior:** Pass `--cleanup=verbatim`, or write the notes to a file and use `-F` with the same flag; the protocol already mandates HEREDOC, which is what hides the stripping. Published tags stay as they are — the protocol's own rule forbids moving or deleting existing tags, and a backfill would rewrite release history for cosmetics. Consumers pick the fix up by re-running `/super-bootstrap:release-init`: [`docs/decisions.md`](../decisions.md) settled that the generated skill is a pure derivative whose overwrite-after-confirm *is* its update channel, so this needs no migration path.
