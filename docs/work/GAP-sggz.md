### Decision needed

- Which mechanism should catch a card whose next step another card's thread or commits finished?
- options:
  - **A — non-ID sweep signal (e), triage-only.** For each open card, match its latest block's next-step topic words against main-line commit subjects and other cards' blocks written *since that block's date* (not only this session). A hit becomes a **triage** move through the existing `:68` lane, never a resolve. This gives the best recall for the jowagoko shape. Cost: false-positive triage rows in the pick, and a word-match rule that the prose must pin.
  - **B — producer-side cross-naming.** When a card's block or commit finishes another card's step, the writer names that card's ID (a line in the Progress / commit-door / log contract). The sweep stays ID-keyed, and (c)/(b) pick it up. There is no pick noise, but it depends on the writer's recall, and that recall is the miss here: three sessions did not name it.
  - **C — no change.** Leave this case to human notice and needs-me. Record it in `docs/decisions.md` as a known blind spot.
- recommendation: A, scoped as triage-only with the since-latest-block window. It is the only option that does not depend on recall that already failed. The existing triage lane bounds its cost to one row per hit, and a hit hands judgment to `/super-bootstrap:triage`, not to the close.
- settles by: the owner's preference on pick noise against recall (preference authority, with row 112 as precedent). Then a `phased build` measurement: a bench fixture shaped like jowagoko (one card whose step another card's block and an unnamed commit finished, plus decoy cards that share topic words), run headless on the dev copy of `session-close`. It measures the hit on the target and false-positive triage rows on the decoys against a no-signal control (the RED that `skill-authoring.md` requires).
