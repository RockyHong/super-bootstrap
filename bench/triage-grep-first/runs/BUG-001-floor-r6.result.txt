**Root cause.** The last two calls in `StatementEngine.run()` are in the wrong order (`engine.py:89-90`). `_emit_period()` ships the statements and clears `_open` before `_rollover(None)` settles the batch's last held refund. That refund then posts onto a new statement that is never returned and gets wiped at the start of the next `run()`. Its amount is never added to the balances either, so both the closing balance and next month's opening balance come out 12.34 too high.

A refund earlier in the batch gets settled by the next event's rollover while its statement is still open. That's why ops' staging replay with the refund moved up worked. The `_rollover` docstring already says the call after the loop is there to settle the trailing refund, so the intended behavior is clear.

**The card's prior (a bad ledger key) is not the cause.** The ledger only explains the second symptom. `_apply_refund` records `R-88120` in the ledger even though it never reached a statement. The re-send `R-88120-b` has the same (account, amount, posted_on) key, so it was correctly skipped as a replay. That key is deliberate, because processors don't always send our refund id back. `refunds.py` stays unchanged.
