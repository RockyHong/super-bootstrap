**Registration rule** (2a / 2a-scale / 2b plantings, 2a-scale / 2b-adopt / 2b Retired artifacts deletions): a durable artifact this run places for the first time or deletes earns its own sync-report row — status `⊕ new` for a planting, `⊘ removed` for a deletion:

```
registration: {artifact} → {surfaces, or none}
```

`{surfaces}` names the consumer-authored surfaces that enumerate the artifact's class — a table or list carrying one entry per member (a glob that already covers the artifact needs no edit and is not a surface; a curated shortlist of a few files is not an enumeration). Grep each of five places for the artifact's path and for its parent directory string (`docs/`, `.claude/skills/`), and name every place whose hit is such a list:

1. `.claude/rules/*.md` `paths:` frontmatter entries that name paths literally
2. root `README.md` — any table or list naming `docs/` paths
3. `docs/**/README.md` and `docs/overview.md` § Module Index
4. `.claude/rules/*.md` bodies — any table or list naming `docs/` paths (ownership / routing)
5. `CLAUDE.md` § Rules (one bullet per path-scoped rule file) and § Planning (one index line per doc) — project-owned registration surfaces, where the section exists. Planting → append the artifact's bullet / index line at the end of the section's list when the section holds none for it; move or deletion → re-point or drop that artifact's own line. The run touches only the line of the artifact the row names and rewrites no other line

The row resolves `updated` once every named surface is edited, before § 2c runs, in the same commit — or `none`, earned only when all five greps return nothing. An unresolved row halts § 2c like a drifted one. The 2a-hooks step sits outside this rule, scripts and `.claude/rules/harness.md` included: the `.claude/settings.json` and `.gitignore` entries that step already writes are its registration.

**Per-doc handling:**

- **Missing** → fill placeholders, write.
- **`CLAUDE.md`** → absent → fill placeholders (§ Placeholders), write. Present → no diff of the file: it stays as the consumer left it, apart from the § Rules / § Planning registration lines this run's plantings and deletions earn (§ Registration rule) and a placed doc rule's § Rules bullet that the bullet's own approved row rewrites (the § Rules bullet below).
- **Exists, drifted in pipeline-owned section** → diff that section vs template — only the part § Pipeline-owned marks drift-checked (a section whose body is consumer-owned, such as `docs/techstack.md` § Staged-Tree Verify's command block or § Packages' rows, diffs its header and fixed note only; a placed doc rule — `ssot-doc-link`, `dimension-discipline` — diffs its `paths:` list on the skeleton's entries only: entries after the skeleton's last one are its consumer tail, which leaves the file `✓ current` and which no drift row removes or reverts, while an entry interleaved among the skeleton's entries is drift, and approving the row moves it into the tail; the rule's `CLAUDE.md` § Rules bullet takes its own row, never this one — next bullet) — present to user, get approval per section, write approved.
- **A placed doc rule's `CLAUDE.md` § Rules bullet** (`ssot-doc-link`, `dimension-discipline`) → every re-run compares the bullet against the rule's current skeleton `paths:` entries, whether the rule file drifted or not. Compare entry by entry, in order: a parenthetical gloss after an entry is ignored, and entries the bullet lists after the skeleton's entries are its consumer tail, never a mismatch. The row is `CLAUDE.md: Rules: {rule file}`. Match → `✓ matches`, shown as `[§ Rules bullet] ✓ matches` in the rule file's Block 1. Mismatch → `⚠ drifted`, a row of its own whatever the rule file's verdict, and Block 2 shows the bullet's before and after lines. Approval rewrites only the bullet's skeleton entries to the skeleton's, and keeps its consumer-tail entries, its parenthetical, its other text and every other line; the row resolves `updated` once the bullet is written. `n — {reason}` resolves `declined ({reason})`, and the decline carries until the skeleton's `paths:` entries change (anchor: § 2c `declined`). No bullet for the rule in § Rules, or no § Rules section → no row: planting a bullet is the § Registration rule's. This row is the only lane that rewrites the bullet.
- **Exists, pipeline-owned section absent** → `⊕ new` row: render the template section at Block 2, get approval, insert at the skeleton-defined position relative to the surviving sections.
- **Exists, seed-once section** (`docs/techstack.md` § Runtime / Framework / Key Dependencies / Build & Distribution, `docs/overview.md` § Problem / User / Current State — § Pipeline-owned) → compare **shape only**: heading present and in its skeleton position → `✓ current`, whatever facts the body carries. Heading missing → `⊕ new` per the bullet above, inserted with this run's detected facts filled in where code is present (the template's placeholder body on a docs-only repo — § Placeholders' docs-only rule, shared with CLAUDE.md § Tech Stack / § Commands; an `overview.md` section always takes the placeholder body, § Placeholders) — that insertion is the section's first fill. The body is never diffed against the template here: a filled body and a still-unfilled placeholder both read `✓ current`. A techstack section's facts that went stale route to the Phase 3 stale-facts advisory (§ Phase 3), never to a write in this walk; an `overview.md` section's body is product prose — never diffed, never advised.
- **`.claude/settings.json` core plugin pin** → key present → `✓ pinned`; key absent → `⊕ new`, resolving `inserted` with no prompt (§ 2a).
- **Exists, current** → mark `✓ current`. **Still show the per-section comparison briefly** (one-line per pipeline-owned section: `[Runtime] ✓ matches`, `[Framework] ✓ matches`, etc.; a placed doc rule adds `[§ Rules bullet] ✓ matches` when its bullet matches) — asserting "current" without showing the comparison is a gap.
- **Project-owned content** → never touched, even on drift.

**Gate — the sync report must exist and cover every pipeline-owned section, plus every artifact the § Registration rule covers, before commit.** Read `.claude/bootstrap-sync-report.md` and cross-check its rows against § Pipeline-owned: every pipeline-owned section that applies to a file in scope must have a row, `.claude/rules/harness.md` must have its one whole-file row (written at § 2a-hooks — `CLAUDE.md` is project-owned and contributes no section row), on a re-run every placed doc rule whose bullet `CLAUDE.md` § Rules holds must have its `CLAUDE.md: Rules: {rule file}` row (§ 2b Per-doc handling), and every durable artifact the § Registration rule covers must have a `registration:` row. Missing file, or any uncovered section or artifact → halt, return to 2b, produce the missing rows. A `⚠ drifted`, `⊕ new`, `⊘ missing`, or `⊘ removed` row must also carry its resolution (`updated` / `inserted` / `seeded` / `declined ({reason})` / `declined (carried: {reason})`), a rot row its own (`migrated` / `declined ({reason})` / `declined (carried: {reason})`), a `registration:` row its own (`updated` / `none`), a language-server pin row also `skipped (user scope: {key})` / `kept (removed)` (§ 2b Language-server pins), a § 2a-hooks row also `kept (fork)` — a fork kept at the overwrite/keep prompt, which stays out of `declined` (`updated (stale)` / `updated (fork, overwritten)` count as `updated`) — an unresolved row, or a `declined` row carrying no reason, halts the same way. A rot outcome line present and reading `no rot scan` halts too — the scanner failed or swept nothing, so its zero rows are not a clean; return to 2b, clear the cause the line names, and re-run `rot-scan.sh`. A fresh install carries no rot line, and the gate reads none. This is a Read + set-difference check, not a self-attestation — a skipped drift check leaves no rows to find, so it cannot pass the gate.

**`covered`** is an array of bare row-identity strings — one string per sync-report row across all three row classes: its per-section rows, its whole-file artifact rows (the § 2a-hooks rows included — the hook scripts and `.claude/rules/harness.md` among them — identity as that step names it), and its rot rows. Each identity is *transcoded* from its report row rather than copied verbatim: the report renders a section row `{file}: {Section}` and the identity is `{file} § {Section}`; a whole-file artifact is its repo-relative path alone; a rot row is `{file} § rot:{old}` — keyed by the stale literal, never the line, since line numbers shift between runs; a placed doc rule's § Rules bullet row is `CLAUDE.md § Rules: {rule file}`. `registration:` rows stay report-only, and so does a pin row resolved `skipped (user scope: …)` — it never inserted the key, so a later run that finds the key absent has no removal to carry.

**`declined`** is the rows resolved `declined` — a drift kept or an insert declined at Block 2, a rot row left alone at the § 2b rot scan — each written `{ "section": "<row identity>", "reason": "<the row's declined reason>", "anchor": "<sha256>" }`, carrying the row's own `covered` identity string and the parenthetical of `declined ({reason})` as the reason — so `declined` stays a subset of `covered`, and marks divergence accepted, not pending. A carried row is a declined row: it writes its entry again with the same reason — the original `{reason}`, the `carried:` marker stripped. The `anchor` is the sha256 of what the decline answers: for a section or whole-file row, this run's rendered template text for that row (placeholders filled, conditional lines resolved — the text the drift check compared against); for a § Rules bullet row, the rule skeleton's `paths:` entry lines; for a rot row, the rename-map entry line (`` `old` `` → `` `new` `` — reason); for a § 2b Retired artifacts row, its § Retired files entry line. Block 2 reads it back on the next re-run to carry the decline or re-prompt.
